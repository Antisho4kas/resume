# План: сайт-резюме «Резюме с доказательствами»

Версия 2 от 22.11.2026. Планирование завершено; текущее состояние реализации описано в `README.md`.

Связанные документы: `CONTACT_FORM.md` (форма связи), `DESIGN.md` (дизайн), `CONTENT.md` (контент), `DECISIONS.md` (решения и проверенные факты).

## 1. Требования владельца

Это исходные требования. Они не меняются без решения владельца.

- Сайт-резюме разработчика на трёх языках: немецком, английском и русском.
- Сайт в первую очередь является резюме: рекрутёр за полминуты понимает, кто перед ним, что он умеет и как с ним связаться.
- Сайт необычный и должен удивить работодателя.
- Сайт показывает навыки владельца и состоит из многих частей, но не перегружен дизайном.
- Есть форма обратной связи: сообщение до 1024 символов, не больше одного сообщения с одного IP за 5 минут, защита от перегрузки сервера большими запросами. Полная спецификация находится в `CONTACT_FORM.md`.
- Основные языки разработки: TypeScript и JavaScript. Другие допустимы там, где они естественны.
- Дизайн опирается на исследование референсов. Его результаты записаны в `DESIGN.md`.

## 2. Концепция

Обычное резюме просит поверить на слово. Это показывает подтверждение. У сайта три слоя:

1. **Документ.** Строгий лист резюме: имя, опыт, навыки, проекты, контакты, PDF.
2. **Доказательства.** У навыков и фактов стоит маркер «проверить». По клику прямо в строке раскрывается живое подтверждение.
3. **Инструменты для инженера.** Палитра команд (Ctrl/⌘K), терминал, публичный API, ссылки на исходники.

Переключатель «Рекрутёр / Инженер» управляет вторым слоем. По умолчанию открыт чистый документ.

У сайта два читателя. Рекрутёр тратит на резюме около полминуты и не должен продираться через интерактив. Технический руководитель хочет убедиться, что за словами стоит умение. Отсюда правила, которые действуют на всех этапах:

- **Документ первым.** Всё, что движется или требует действий, появляется только по клику посетителя.
- **Доказательства настоящие.** Панель показывает реальные данные сборки, CI или ответа сервера. Если данных нет, панель скрыта.
- **Лёгкий первый экран.** Тяжёлые модули загружаются только по клику.
- **Честные уровни.** Навык с пометкой «основы» остаётся основами. Ничего не завышаем.

## 4. Проекты

На сайте показаны два проекта. Остальные проекты владельца на сайте не показываем.

В листе резюме у каждого проекта есть карточка: строка результата, роль владельца, стек, ссылка на разбор. Разборы устроены одинаково: что это за проект, роль и период, что сделано, как устроено (схема), разрешённые визуальные материалы, ссылки, честная пометка статуса.

### Finzli: командный проект

- **Что это:** платформа аналитики крипторынка в реальном времени, `finzli.com`.
- **Роль владельца:** frontend, QA, настройка AWS для базы данных и хостинга и настройка агента для анализа на Amazon Bedrock. Остальные части продукта владельцу не приписываем. Подтверждённые факты о периоде и команде — в `CONTENT.md`.
- **Разбор:** три блока по ролям.
  - Frontend: подтверждённый вклад в интерфейс, JavaScript, TypeScript и работа с API.
  - QA: только подтверждённые сведения о тестировании.
  - AWS: схема настроенных владельцем частей, включая аналитического агента.
- **Материалы:** карта вклада и ссылка на публичный сайт `finzli.com`. Скриншоты и записи экрана не показываем. Ссылка показывает продукт, а не доказывает авторство отдельных функций.

### SucheWohnung: личный проект

- **Что это:** агрегатор объявлений о квартирах в Германии с уведомлениями в Telegram. Публичный репозиторий `Antisho4kas/SucheWohnung`.
- **Роль владельца:** единственный разработчик, архитектура и реализация.
- **Разбор:** схема конвейера collect, match, notify; стек; тесты и CI; развёртывание и эксплуатация на VPS без секретов и данных доступа. Владелец подтвердил, что проект работает.
- **Мини-пример** (этап 6): посетитель задаёт фильтр и видит совпавшие объявления и превью уведомления в Telegram. Данные только синтетические. Если модули `filters` и `matching` из `packages/shared` отделяются от базы данных, пример исполняет настоящий код проекта. Иначе делается упрощённая версия с честной подписью.
- **Подача:** показываем движок и архитектуру, без акцента на сборе данных с конкретных порталов. Экраны только на тестовых данных.

### Правила для живых материалов

- По умолчанию карточка статична. Пример или запись открывается по клику.
- Автозапуска нет, учитывается `prefers-reduced-motion`, одновременно движется не больше одного элемента.
- Пример понятен за 10–15 секунд: одно действие, один результат, подпись «что здесь происходит», ссылка на исходник.
- Код примера не попадает в первый экран.
- Подписи честные: «тестовые данные», «запись экрана», «прототип».
- На телефоне пример работает пальцем или заменяется кадром.

## 6. Стек и инфраструктура

- **Приложение:** Next.js 16 (App Router, `output: 'standalone'`), React 19, TypeScript в строгом режиме, Tailwind CSS 4, next-intl 4. Локали обрабатывает `proxy.ts`: в Next.js 16 он заменил `middleware.ts`.
- **Контент:** единый источник в виде файлов резюме на трёх языках со схемой zod. Из него собираются страница, API, PDF, терминал, SQL-база и подпись, поэтому версии не расходятся.
- **Сервер:** Route Handlers на Node.js, Redis для лимитов формы, Telegram Bot API для доставки сообщений.
- **Хостинг:** собственный VPS владельца. Docker Compose с сервисами `app`, `redis`, `caddy`, `cloudflared`. Вход только через Cloudflare Tunnel, наружу открыт один SSH. Caddy ограничивает размер тела запроса и таймауты и передаёт приложению реальный IP посетителя.
- **Шрифты и ресурсы:** всё раздаётся с собственного домена, без сторонних CDN, трекеров и cookies аналитики.
- **Другие языки:** SQL, Bash, Dockerfile, Caddyfile, YAML там, где они естественны.

Точные версии и подтверждающие факты записаны в `DECISIONS.md`.

## 7. Три языка

- Адреса с префиксами `/de`, `/en`, `/ru`. С корня идёт редирект по языку браузера, запасной язык английский, выбор запоминается.
- Строки интерфейса лежат в `messages/{locale}.json` с ICU-плюрализацией. Контент резюме хранится отдельно по языкам. Тест следит, что структура совпадает во всех локалях.
- `hreflang` и `x-default`, локализованные метаданные и OG-картинки, JSON-LD `Person`.
- Переключение языка не сбрасывает позицию на странице.
- Немецкая версия вычитывается отдельно: она основная для целевого рынка.

## 8. Качество

- **Тесты:** unit и интеграционные на Vitest (обработчик формы проверяется с настоящим Redis и подставным Telegram), сквозные на Playwright по трём локалям на десктопе и мобильном, проверка доступности axe.
- **CI (GitHub Actions):** lint, проверка типов, тесты, сборка, e2e, Lighthouse CI, образ в GHCR, деплой на VPS, smoke-тест `/api/health`.
- **Бюджеты:** Lighthouse не ниже 95 по всем категориям на странице резюме, без нарушений axe, без сдвигов макета.
- **Доступность:** семантическая разметка, работа с клавиатуры, видимый фокус, контраст, `prefers-reduced-motion`.
- **Зависимости:** только версии старше 7 дней. Секреты хранятся в GitHub Secrets и в `.env` на сервере.

## 9. Этапы

Каждый этап начинается со списка тестов и заканчивается отчётом владельцу. Этап 5 можно начать сразу после нулевого, как только у владельца будут сервер и домен: тогда каждый следующий этап сразу попадает в прод.

### Этап 0. Каркас

- Next.js, TypeScript и Tailwind в корне репозитория. Маршруты сразу под сегментом `[locale]` для `de`, `en`, `ru` со страницей-заглушкой.
- ESLint, Prettier, Vitest с первым тестом, Playwright со smoke-тестом трёх локалей.
- CI в GitHub Actions: установка, lint, проверка типов, unit, сборка, e2e.
- `.env.example`. Раздел «Команды» в `AGENTS.md` заполнен реальными командами.

Готово, когда: lint, проверка типов, тесты, сборка и e2e проходят локально, а после пуша и в CI.

### Этап 1. Контент

- Схема zod для резюме и разборов, три файла контента, тест на совпадение структуры локалей.
- Тексты резюме и двух разборов. Источники и правила описаны в `CONTENT.md`, факты подтверждает владелец.

Готово, когда: тесты схемы и паритета проходят, владелец подтвердил тексты на трёх языках.

### Этап 2. Дизайн и документ

- Прототип первого экрана, листа резюме, карточки проекта и страницы разбора на согласование владельцу.
- После согласования: токены, типографика, светлая и тёмная темы, адаптив, стили печати, секции резюме, две карточки проектов, страницы разборов (текст, таблица фактов, схема и материалы по правилам раздела 4).

Готово, когда: владелец принял прототип, есть скриншоты Playwright на десктопе и мобильном в трёх локалях, axe не находит нарушений, бюджеты Lighthouse соблюдены.

### Этап 3. Языки

- Переключатель без потери позиции, полные переводы интерфейса, редирект с корня, запоминание выбора.
- `hreflang`, локализованные метаданные, атрибут `lang`.

Готово, когда: e2e покрывают переключение и редирект, тест паритета проходит.

### Этап 4. Форма связи

- Реализация по `CONTACT_FORM.md`, начиная с обязательного списка тестов.
- Доставка в Telegram через адаптер с подставной реализацией в тестах. Состояния интерфейса на трёх языках.

Готово, когда: проходят все обязательные тесты из спецификации, владелец получил тестовое сообщение в Telegram с настоящим токеном.

### Этап 5. Первый релиз

- Dockerfile (многоэтапный, без root, с healthcheck), Compose, Caddyfile.
- Настройка и защита VPS: вход только по ключам, файрвол, автообновления.
- Cloudflare Tunnel и DNS, заголовки безопасности и CSP.
- Деплой из CI: образ в GHCR, обновление на сервере, smoke-тест, описанный откат.
- Правовые страницы, если владелец решил их делать.

Готово, когда: сайт открывается на домене в трёх локалях, форма работает в проде от отправки до Telegram, сервер недоступен в обход Cloudflare, smoke-тест в CI зелёный.

### Этап 6. Живые материалы проектов

- Мини-пример SucheWohnung на синтетических данных.
- У Finzli карта вклада и ссылка на публичный сайт, без скриншотов и записи экрана.

Готово, когда: материалы соответствуют правилам из раздела 4, e2e покрывают мини-пример, первый экран не потяжелел.

### Этап 7. Первая волна доказательств

- Ссылки на исходники, публичный API с OpenAPI и консолью, панель защиты формы, происхождение сборки, отчёт о тестах, паспорт безопасности.
- Переключатель «Рекрутёр / Инженер».

Готово, когда: каждая панель показывает реальные данные и скрывается при их отсутствии, поведение покрыто тестами.

### Этап 8. Вторая волна доказательств

- Терминал, палитра команд, SQL-консоль, путь запроса, подпись резюме и её проверка.

Готово, когда: модули загружаются только по клику, работают на трёх языках и покрыты тестами.

### Этап 9. PDF и SEO

- PDF на трёх языках, которые CI собирает из печатной версии. OG-картинки, JSON-LD, sitemap и robots, vCard.

Готово, когда: PDF совпадают с содержимым сайта и обновляются автоматически при каждом релизе.

### Этап 10. Полировка

- Аудит доступности и скорости, вычитка текстов на трёх языках, страницы ошибок, проверка в основных браузерах.

### Этап 11. По желанию владельца

- MCP-эндпоинт и `llms.txt`, страница «Как сделан этот сайт».

## 10. Риски

- **Объём.** Частей много, поэтому каждая волна доказательств состоит из независимых модулей, которые можно отложить без ущерба для резюме.
- **Перегруз.** Интерактив способен задавить документ. Правило «документ первым» проверяется на каждом этапе.
- **Свежие мажорные версии.** Next.js 16, Tailwind 4, Vitest 5 и TypeScript 7 вышли недавно. Перед использованием API сверяемся с документацией.
- **Правовые страницы.** Нужны ли Impressum и Datenschutzerklärung, решает владелец. Это не юридическая консультация.
- **Командный проект.** Для Finzli не подменяем описание личного вклада описанием всего продукта и не публикуем скриншоты.

## 11. Что требуется от владельца

В скобках указан этап, к которому нужно действие.

- Первый пуш для прогона GitHub Actions (0). Коммит и пуш выполняются только по явной просьбе владельца.
- Подтверждение текстов на трёх языках по источникам из `CONTENT.md` (1).
- Бот Telegram: токен и chat_id владелец кладёт в секреты сам (4).
- Сервер и домен (5).
- Решение по Impressum и Datenschutzerklärung (5).
